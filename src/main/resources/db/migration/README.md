# 資料庫結構變更 (Schema Migration) — 從現在起改用 Flyway 自動管理

## 這是在解決什麼問題

以前每次改資料庫結構 (加欄位、改欄位長度...) 都是寫一支 `db/migration_xxx.sql`，然後**手動**去資料庫
執行。這種做法很容易忘記跑，常常是部署完程式、使用者實際操作時才發現「Unknown column」這種錯誤，
系統才會在使用中噴出白畫面（Whitelabel Error Page）。

**改用 Flyway 之後**：資料庫要改的 SQL 檔案放在這個資料夾（`src/main/resources/db/migration/`），
程式一啟動，Flyway 會自動檢查資料庫目前套用到哪個版本、把還沒套用的 SQL 依序、自動執行完，
不用再手動跑，也不會漏跑。

## 怎麼加一個新的資料庫變更

1. 在這個資料夾新增一個檔案，命名規則是 **`V{數字}__{說明}.sql`**（兩個底線）：
   - 數字要比目前資料夾裡最大的數字再大 1（例如目前最大是 `V3`，新的就叫 `V4`）
   - 說明用英文/底線，例如 `V4__add_flight_number_to_itinerary_item.sql`
2. 把 SQL 寫進去，正常寫就好，不用加什麼特殊語法：
   ```sql
   ALTER TABLE itinerary_item ADD COLUMN flight_number VARCHAR(50) NULL;
   ```
3. 存檔、重新啟動程式（或部署上去），Flyway 會自動偵測到這個新檔案並執行。

## 重要規則（一定要記住）

- **已經部署出去、Flyway 執行過的檔案絕對不要再修改內容**——Flyway 會記錄每個檔案的內容雜湊值，
  如果內容被改過，下次啟動會直接報錯拒絕啟動（這是刻意設計，防止「偷改已經跑過的歷史紀錄」）。
  如果真的寫錯了，正確做法是**新增一支新的檔案去修正**，不是回頭改舊檔案。
- 檔名數字絕對不能重複、也不要跳號跳太多（維持連續遞增就好，不用特別留空號）。
- 每支檔案盡量只做「一件事」，方便追蹤跟之後回頭看是哪一版做了什麼變更。

## 目前資料夾是空的，為什麼？

因為這個專案是「中途」才導入 Flyway 的，不是一開始就用 Flyway 建的。在導入的當下，
系統已經用 `db/` 資料夾（專案根目錄，不是這個資料夾）裡累積的一堆手動 SQL 檔案跑到某個狀態了。
Flyway 沒辦法（也不需要）重新驗證那些舊檔案——而是直接把「導入 Flyway 那一刻的資料庫狀態」
當作起點（這叫 **baseline**，設定在 `application.properties` 的
`spring.flyway.baseline-version=1`），從那之後新增的變更才會放進這個資料夾、被 Flyway 接管。

**部署這次更新之前，記得先執行 `db/before_flyway_catchup.sql`**（專案根目錄的 `db/` 資料夾，
不是這個資料夾），確保舊的手動 SQL 檔案都補齊了，才不會把「還沒套用的舊變更」也一起誤判成
「baseline 已經涵蓋」而永遠不會被執行。
